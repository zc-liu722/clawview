# 0. 一句话结论

**不要做一个新的聊天工具，也不要赌国内 IM 插件。**
最终产品应该做成：

**“面向移动端的 OpenClaw 透明控制台”**
形态是 **聊天内回执链接 + 手机 Web App 控制台 + 轻量桌面端辅助**。

它的本质不是 another dashboard，而是：

**把 OpenClaw 从“黑盒机器人”变成“可见、可懂、可控、可放心花钱”的数字员工。**

这条路最符合四个条件：

* 技术实现最稳
* 用户价值最直接
* 渠道推广阻力最小
* 后续利润空间最大

OpenClaw 当前确实已经有 typing indicators、`/status`、`/usage`、session/transcript、memory index 等底层能力，但它们主要分散在文档、CLI、配置和日志层，对普通用户并不构成“产品体验”。这意味着你不是和官方正面冲突，而是在做一个非常明确的**体验层缺口**。([OpenClaw][1])

# 1. 最终产品思想

## 产品定义

产品名先用代号：**ClawView**

一句话定位：

**让你第一次看清 OpenClaw 在干什么。**

更完整的定义：

> ClawView 是 OpenClaw 的移动端透明层。
> 它负责把状态、步骤、成本、记忆、异常和权限，从工程日志翻译成普通人一眼能懂的控制界面。

你要解决的不是“AI 不够强”，而是四个更本质的问题：

1. **用户不知道机器人有没有活着**
2. **用户不知道它在花多少钱**
3. **用户不知道它是怎么得到结果的**
4. **用户不知道它记住了什么、读了什么、用了什么**

这四个问题本质上都归到一个词：

**信任基础设施。**

# 2. 为什么现在做，窗口成立

OpenClaw 现在的产品形态，本身就非常适合催生你这种衍生层。它运行在用户自己的设备上，接入用户已经在用的聊天渠道，如 WhatsApp、Telegram、Slack、Discord、Google Chat、Signal、iMessage、Feishu 等；官方也强调 Gateway 是控制平面，真正的产品是“助理本身”。这说明它天然是一个“底座型 agent”，而不是成熟的终端消费品。([GitHub][2])

中国市场窗口也是真实存在的。最近中国出现了明显的 OpenClaw 热潮，用户把它用于副业、安排日程、股票、陪伴等场景，一些地方还给相关创业项目提供补贴和办公资源；与此同时，监管和媒体又开始集中放大安全、权限、数据泄露和误用风险。也就是说，市场同时出现了两股力量：**强需求**和**强焦虑**。这正好给“透明层、控制层、审计层”留出位置。([Business Insider][3])

# 3. 最终决定：做什么，不做什么

## 3.1 做什么

做成三层一体的产品：

### A. 聊天内轻入口

机器人在原聊天渠道里回复一张简洁卡片：

* 正在执行
* 预计还需多久
* 已花 token / 金额
* 一个按钮：**查看实时过程**

这个入口只负责“把人拉到控制台”。

### B. 手机 Web 控制台

这是核心产品。用户点开就能看到：

* 在线 / 离线 / 思考中 / 调工具中 / 等待授权 / 出错
* 实时步骤流
* 本任务与今日成本
* 机器人记忆中心
* 任务历史与异常回放

### C. 轻桌面端辅助

给重度用户和创作者一个桌面小窗：

* 状态灯
* 异常弹窗
* 成本预警
* 快速打开任务页

这层不是 MVP 必做，但中期能提高留存和使用频率。

---

## 3.2 不做什么

### 不做新的 IM/聊天软件

原因很简单：用户不会为了“看机器人状态”而迁移自己的聊天习惯。OpenClaw 的优势本来就是复用既有渠道。你逆着这个路径做，等于自断传播。([GitHub][2])

### 不赌“国内主流通讯软件插件”

国内主流平台对聊天界面级插件支持极弱，且审核、权限、接口稳定性都不适合作为创业公司的主干。你可以做“连接层”，但不要把公司命运押在平台插件上。

### 不从第一天就做成开发者 observability 平台

LangSmith、Langfuse、AgentOps、Helicone 已经覆盖 tracing、session、cost、tool usage、监控、成本分析等工程侧能力。你的机会不在“我也能追踪 trace”，而在“我能把 trace 变成小白愿意天天看、愿意付费的体验”。([LangChain Docs][4])

# 4. 最终产品形态

## 4.1 用户感知方式

用户不应该觉得自己在用“监控软件”，而应该觉得：

**“我终于能看见我的 AI 助理在工作了。”**

用户侧体验要像下面这样：

### 场景 1：聊天中发起任务

用户在微信/Telegram/飞书里说：

> 帮我整理今天的客户线索并生成跟进建议

机器人立即回：

> 已开始处理
> 当前状态：正在搜索资料
> 已用 1,240 tokens / 约 ¥0.12
> [查看实时状态]

用户点开 H5 页面，看到：

* Step 1：读取 CRM 备注
* Step 2：搜索相关公司资料
* Step 3：提炼跟进建议
* Step 4：生成回复草稿

这就是你最核心的“爽点”。

### 场景 2：用户担心机器人失联

页面顶部明确显示：

* 设备在线
* Gateway 正常
* 最近心跳时间
* 最近一次响应时间
* 若异常，告诉用户是“机器人正在思考”“模型接口拥堵”“设备离线”“授权失效”

OpenClaw 官方确实提供 typing indicators、`openclaw status`、`gateway status`、`channels status --probe` 这样的诊断能力，但它们是工程命令，不是给普通用户的解释界面。([OpenClaw][1])

### 场景 3：用户担心乱花钱

页面持续显示：

* 本任务花费
* 今日累计
* 本月累计
* 本次主要消耗在哪个模型
* 超预算提醒

OpenClaw 当前已经支持 `/status`、`/usage off|tokens|full`、`/usage cost` 以及 CLI 的 usage breakdown，这给你提供了很好的成本数据基础。([OpenClaw][5])

### 场景 4：用户担心被“记住”

打开记忆中心，看到：

* 机器人记住了什么
* 来源自哪次对话/哪份文件
* 最后一次被使用时间
* 一键删除 / 设为不再引用 / 设为 7 天后过期

OpenClaw 本身支持 `MEMORY.md`、`memory/*.md`、vector memory search，并默认监控记忆文件变化。你要做的是把“索引能力”升级成“用户可治理的记忆产品”。([OpenClaw][6])

# 5. 最终产品结构

## 5.1 MVP 只做五个功能

这五个功能最容易爆、最容易传播、最容易卖：

### 1. 状态灯

在线、离线、思考中、调工具中、等待授权、错误。
这是最底层的安心感。

### 2. 任务步骤流

把 transcript、tool usage、session history 翻译成“人话步骤”。
OpenClaw 已有 session tools 可列出会话、读取历史、获取 transcript 相关信息，这让“步骤流”有底层基础。([OpenClaw][7])

### 3. 实时 token / 金额

本任务、今日、本月。
加预算上限与异常提醒。

### 4. 记忆中心

查看、搜索、删除、设过期。
用“机器人记住了什么”而不是“memory index”去表达。

### 5. 异常告警

循环调用、成本异常、工具失败、设备离线、权限失效。
用户对 agent 最大的不信任，很多都来自“我不知道出错了”。

# 6. 技术路径

## 6.1 核心原则

**尽量不 fork OpenClaw，不改其主路径，做“旁路采集 + 翻译 + 展示”。**

这样你的技术风险最低，兼容性最好，也最容易随官方升级而继续存活。

---

## 6.2 技术架构

整体架构：

1. **OpenClaw Runtime Adapter**

   * 采集运行状态、session、transcript、tool result、usage、memory 索引变化
   * 尽量通过官方已有表面来接，不深侵内核

2. **Event Collector**

   * 接收事件并标准化
   * 统一为 `task_id / session_id / step / tool / model / usage / memory_hit / status`

3. **Realtime Stream**

   * WebSocket / SSE 推送到移动端页面
   * 手机端刷新步骤、状态、金额

4. **Narrative Engine**

   * 把技术事件翻译成用户可读步骤
   * 例如把 `sessions_history + tool_result_persist + transcript` 转成“正在读取 3 个网页”

5. **Memory Governance Layer**

   * 把 MEMORY 文件、索引召回、引用关系变成“可查看、可删除、可设过期”的 UI

6. **Mobile Web App**

   * H5/PWA 优先
   * 后续可包成轻应用或桌面端

OpenClaw 提供 session tools、tool result hooks、配置层、会话持久化、transcript 结构与 session management deep dive，这些都意味着你可以以“低侵入”的方式把事件侧拉出来。([OpenClaw][7])

---

## 6.3 最容易实现的接法

推荐优先级如下：

### 路线一：日志 / transcript / usage 旁路采集

优点是快。
从 session transcript、usage 输出、memory 文件变化和运行状态命令结果入手，先做出 70% 体验。

### 路线二：插件 / hook 增强

OpenClaw 文档里已有 `tool_result_persist` 等 hook，可在工具结果持久化前同步调整 payload。你可以借这个表面插入更多结构化事件。([OpenClaw][8])

### 路线三：深集成适配器

等你真正跑起来，再做版本化 adapter，兼容更多 OpenClaw 发行版和未来更多 agent 框架。

---

## 6.4 为什么先做 Web / PWA

因为这是唯一同时满足四点的方案：

* 对国内外聊天渠道都通用
* 手机端即开即用
* 不受平台插件审核制约
* 便于传播、截图、分享和埋点增长

# 8. 竞争与差异化

## 8.1 你真正的竞争对手不是 OpenClaw 官方

OpenClaw 官方当前更像 agent 底座和能力层，不是“普通用户透明体验产品”。官方已有 typing、usage、memory、session、status 等基础设施，但它们主要是命令、配置、日志和文档入口。([OpenClaw][1])

## 8.2 你也不是 LangSmith / Langfuse / AgentOps / Helicone

这些产品已经很好地做了开发者 observability：

* LangSmith 强调 trace、监控和端到端可见性。([LangChain Docs][4])
* AgentOps 强调 session、replay、成本、错误、工具使用。([docs.agentops.ai][10])
* Helicone 强调成本跟踪、日志、缓存、限流和 observability。([docs.helicone.ai][11])
* Langfuse 也提供 agent tracing、session tracking 和 token/cost tracking。([Langfuse][12])

你的差异化一句话就够：

**他们卖给工程团队“追踪”。你卖给普通用户“看懂”。**
